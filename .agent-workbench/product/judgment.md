# AgentUI — Judgment

## Round 1 — 2026-09-25, target: idea.md

Market file absent at time of judging — competitive claims here are internal-only; re-check against market.md when it lands. The prior-art list in the brief (line 45) is itself the competitive picture and is used below.

Bottom line first: the stated ambition ("become the default… displacing React + Tailwind", line 33) is dead on arrival, for one structural reason (H1) that no amount of execution fixes. The residual product — a schema-driven screen generator for agent-built internal tools — is viable-shaped but is Retool-with-an-agent, not a React killer, and three of its own strongest features (fixed tokens, 15 primitives, embedded-island integration) all converge on that smaller market. Six holes below; the riskiest assumption and its days-scale test close the round.

---

**H1 · dead-ambition / adopter-incoherence — "Primary: AI coding agents … acting for a human developer" (line 28)**
The agent cannot adopt anything. It runs what its system prompt, skill, and repo config say; its priors are React because its training data is React. So the real adopter is the human operator who must actively mandate AgentUI against their own React knowledge, per project, forever. Worse, "the framework agents use" is not a product category — it is a feature of agent products, and the brief's own prior-art line concedes the incumbents: "v0.dev / bolt.new / Lovable … all output React/Tailwind" (line 45). Those vendors are the agent-UI layer; if a constrained schema made agents better, they would ship it as an internal artifact format (Claude Artifacts already runs a curated component allowlist) — they will not adopt an external one, and their gravity beats a startup's. Realistic best case: niche, reached by skill/system-prompt distribution into agent tools, for teams standardizing internal-tool screens. "Default" is not on the outcome tree.
Test (days): write the ~2,000-token grammar as a skill + repo rule today — zero code, the schema is a doc — install in 2–3 real agent tools, and measure (a) whether agents comply without mid-session drift back to React and (b) whether any human operator prefers the outputs enough to keep the rule installed.

**H2 · ecosystem-moat — every integration path leaks where the spec needs it sealed (line 38)**
(a) Wrapper/escape-hatch nodes: React components take functions, refs, and render props — none JSON-serializable — so only data-only components (charts, basic pickers) wrap cleanly; every wrapped node is also invisible to `tree`, killing the verification story exactly where the hard parts live. (b) Compile-to-React: the value collapses to "a shorter way to write JSX," which is the Pug/Slim/HAML grave the brief itself cites (line 45); and the human inherits machine-generated React nobody can maintain. (c) Embedded as one component in an existing app: cannot share the host's nav, auth, or design system without path (a); works only for isolated pages — i.e., the Retool niche. (d) Wrapping npm into the catalog: a human-maintained treadmill that can never round to npm's size; the first "date-range picker with timezones" request ends the demo. Note the structural bind: paths (b)/(c) reintroduce React and its problems; paths (a)/(d) break `check`/`tree`/analyzability. The moat and the two headline value props are in direct tension — pick one.
Test (days, no renderer): hand-write wrapper specs for the 10 most-requested npm components (date-picker, virtualized table, rich editor, chart…). Each one needing a function prop or imperative handle is a datapoint that the catalog cannot be agent-sufficient.

**H3 · expressiveness ceiling + boundary migration — "~15 primitives … Non-Turing-complete" (line 19), "events as declared actions (POST /follow/{id})" (line 24)**
Declared server actions cover fetch-and-render; drag reordering, optimistic updates, undo, multi-step conditional forms, virtualization, canvas live inside none of the 15 primitives. The escape hatch ("drop to React for the hard 10%") makes the agent bilingual — it must now know both systems and the glue, the least reliable kind of agent work — and the boundary migrates, because the 10% grows with every real screen. Also, non-Turing-completeness is a red herring as a safety pitch: CSS is not Turing-complete either and is the most-hallucinated item on the brief's own problem list (line 10). Termination was never the failure mode; vocabulary and non-locality were, and the escape hatch reintroduces both.
Test (days): take 20 screens from real agent-built apps, mark what fraction is expressible in the 15 primitives with no escape hatch. That fraction is the addressable market, measured before writing a renderer.

**H4 · verification verifies rendering, not design — "Output looks good without a designer" (line 23)**
`tree` (a11y dump) shows structure, not layout: overflow, truncation, overlap, and spacing rhythm are invisible in it. `shot` shows pixels, but a vision model judging screenshots has no taste prior that didn't come from human-designed web — the judgment is circular. Cost side: screenshot-per-iteration is seconds and vision tokens per loop, tolerable alone, but it is the only check once custom nodes exist (H2a). And the fixed token menu guarantees convergence: every output looks the same, which is a feature for a prototype and an auto-reject for any team with a brand — the design system will not match theirs. Three of the brief's strongest-sounding features (fixed tokens, small primitive set, island embedding) independently narrow the buyer to no-designer, internal-tool, prototype work. The claims are consistent; the market they describe is small.
Test (days): generate 20 screens, blind-show to 5 developers with one question — "would you ship this to your users?" — and separately instrument one real agent task with a shot-per-iteration loop to get actual cost/latency per screen.

**H5 · human handoff — "the human developers who supervise them and must maintain the output" (line 29)**
Maintenance reality: stack traces bottom out in a generic renderer (a rendering bug is a bug in AgentUI, unfixable by the user); devtools show generated div soup with no source correspondence; the JSON has no composition or reuse mechanism — no "UserCard," so subtrees get copy-pasted, and a 10-screen app is a wall of duplicated JSON. The sugar notation softens authoring, not debugging. And "every document terminates, renders" (line 19) is a forever-backward-compatibility commitment being made pre-1.0. The brief already fears this (line 41); it is not a docs problem, it is structural. Survivable only if the output is positioned as regenerable/throwaway — which, again, is the internal-tools niche, not product teams.
Test (days): hand one non-trivial screen's JSON + sugar to 5 React developers, ask for a real change (reorder sections, add a conditional block), and time them against the same change in React. If handoff takes 5x longer, the secondary user (line 29) is a non-buyer.

**H6 · v1 is three products — schema+validator, renderer+CLI, notation+formatter (lines 19–22)**
None delivers standalone value: the schema alone is a doc, the renderer without adoption is a tree falling in an empty forest, the notation without the runtime is Pug. Ship-all-three-or-nothing is the classic never-ships shape. But notice the drift: of the four problems in the brief, the best-evidenced one is "No self-verification loop" (line 13), and it is solved by `shot` + `tree` — which need no schema at all and would improve agent-built React today. The how (a new framework) overshoots the why (agents can't see what they built). The one piece with standalone value is the agent-side verification tooling aimed at existing stacks.
Test (days): ship `shot`/`tree` for React as a skill and see whether agents and operators adopt verification alone. Adoption of that is the cheapest signal that the underlying problem is real, before betting on the framework.

---

**Riskiest assumption (the one thing that kills it if wrong):** that an agent working from a ~2,000-token in-context grammar produces *better* UI than the same agent in React — because all of its design competence, not just its vocabulary, is trained on React-shaped examples; grammar-in-context fixes recall, not taste.
Cheapest test (days, not months): spend one day writing the grammar + a JSON validator (no renderer), point 3–5 real agent products at 10 representative screen tasks with and without it, and blind-score both outputs with human judges. If the React baseline wins, every other question here is moot; if the grammar wins, H1's skill-distribution path has its first evidence.
