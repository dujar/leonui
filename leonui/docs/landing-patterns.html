Landing pages

A marketing page is mostly motion and layout — which is exactly the half of the web the platform already does well, and the half a framework should stay out of. leonui contributes one attribute (ui:reveal), a handful of enhancers, and one rule about where an animation may hide things. Everything else is your CSS.

The full page these patterns came from is /pages/landing.html — a complete, copyable landing page with a sticky header, a mobile menu, an animated hero, a logo marquee, a feature grid, a stats band, pricing, a testimonial, an FAQ and a closing form.

The animated hero

An entrance reveal is the most-copied pattern on the page, and it is five attributes:

Three props, and each one is a decision you would otherwise make in JavaScript:

  • trigger="load" — animate immediately, rather than waiting for the element to enter the viewport. Use it for the hero, which is on screen already.
  • stagger="0..4" — a delay in 80ms steps, so five parts arrive in sequence instead of in a heap. It is a custom property (--ui-reveal-delay) set on the element, which is why your own CSS can read the same value.
  • from="fade|up|down|left|right|zoom" — the axis it travels on. Default up, which is the one that reads as “arriving”.

Stats that move

The number is static text; the bar carries the movement. That is deliberate, and it is the honest version of the pattern.

A digit-by-digit count-up needs @property and a CSS counter, and there is no reliable way to feature-query @property — so a page that does it cannot tell a browser that supports it from one that does not, and the fallback is a wrong number rather than no animation. leonui ships the version that degrades to a correct number, and the numbers stay in your markup where search engines and screen readers can see them.

Where an animation may hide something

This is the one rule worth memorising, because breaking it is invisible on the machine you are building on and expensive everywhere else. An animated element needs an “armed” state — the state it waits in. That state must be:

  1. scoped to .ui-reveal-ready, a class only the runtime sets on <html>. A page whose bundle 404s, whose CDN is blocked, or where JavaScript is off never gets the class, so nothing is ever hidden. A landing page whose hero is invisible because a bundle failed is the worst outcome this pattern can have.
  2. inside @media (prefers-reduced-motion: no-preference). A reader who asked for less motion gets the page, not a fade.
  3. separated from the transition. Declare transition on the revealed state, not the armed one. A transition runs when the new computed style declares one, so declaring it on the armed state makes arming animate too — the page slides itself away on load and only then slides back.

All three rules are visible in the stats example above. The framework's own ui:reveal follows them in src/ui.css, which is worth reading as the reference implementation.

Pricing with a billing toggle

One boolean signal, one checkbox, two computed prices, and no event wiring:

Two things here are easy to get wrong and are called out in the example's own comments. A checkbox holds a boolean, so it takes ui:bind-checked plus a toggle verb — ui:model writes the string .value, which for a checkbox is always "on". And ui:computed takes one declaration per element, unlike ui:state and ui:bind which split on ;; a second declaration goes on its own element. ui check names both mistakes if you make them.

FAQ, and the platform's own accordion

<details> + <summary> opens with no JavaScript, is keyboard-operable for free, and its content is findable by in-page search — three things a hand-rolled accordion has to re-implement and usually does not. ui:acc supplies the styling and the marker rotation; it implements none of the behaviour. Reveal and <details> compose without ceremony: the reveal animates the row in once, and the row keeps its own open and close afterwards.

What else the page uses

  • Sticky header + mobile menu: popover and popovertarget are the platform's own, so the menu is ui:popover for the styling and the invoker button for the behaviour. Note the scroll-margin-top in the page CSS — without it every in-page anchor lands underneath the sticky header.
  • Logo marquee: a CSS @keyframes on transform with the track's contents duplicated. It is inside a prefers-reduced-motion: no-preference guard, so it is simply a static row for anyone who asked for less motion.
  • Feature grid: ui:reveal with stagger 0/1/2, repeated per row, so each row of cards cascades.
  • Closing form: ui:model on the email field, and a verb list that toasts and clears the field in one go — ui:fx="submit: toast 'Thanks — …' + email; set email = ''". The runtime preventDefaults submit, so a leonui form never navigates.
