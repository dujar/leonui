Components

A leonxstream component is a subtree: markup, its own state, and its behavior live together in one place. There are three ways to make it reusable, in increasing order of packaging. All three keep the same contract: props are attributes (plain data), state is per-instance, behavior rides with the markup.

1. A subtree is a component

Any element carrying ui:state is an independent instance. Copy the block, get a second widget with isolated state — scoping is by ancestor, so nothing leaks between them. This is the zero-mechanism baseline and it is already tested behavior (see State & binds → scoping).

2. ui:use — write once, instantiate many (recommended)

Define the component once in a <template>. Host attributes become prop signals; ui:state inside the template is per-instance state.

RuleDetail
Propsevery host attribute except id, class, style; values are coerced (number / boolean / JSON like ui:state)
Stateui:state inside the template = one per instance; props and state are both visible to the subtree (nearest scope wins)
Behaviorui:fx inside the template attaches per clone — handlers never cross instances
Nestingtemplates may contain ui:use of other templates
Wheresame page; for cross-page reuse, the pattern is your server include / a shared partial — the format stays plain HTML

3. Custom elements — a component others install

When a component must be distributed (a design system, an npm package), wrap it in a custom element whose markup is leonxstream. The runtime exports attach exactly for this:

import { attach, coerce, scopes, sig } from '/dist/leonxstream.js';

class XCounter extends HTMLElement {
  connectedCallback() {
    const start = coerce(this.getAttribute('start') ?? '0');
    this.innerHTML = `…ui:* markup…`;
    scopes.set(this, { signals: new Map([['n', sig(start)]]), meta: new Map() });
    attach(this);   // full runtime passes, scoped to this element
  }
}
customElements.define('x-counter', XCounter);

Page authors just write <x-counter label="votes" start="5"> — attributes as props, behavior included, theming via the same tokens. This is the Tier-3 path from the design: interaction-rich widgets ship as elements; the page grammar stays closed and checkable.

Which one when

MechanismUse when
Subtree + scoped stateone-off widget, no repetition
ui:use templaterepeated inside a page — the default choice
Custom elementreused across pages/projects, or by consumers who only see a tag

Variants (variant="primary|ghost|…") and tokens are the styling half of reuse: a component varies through the catalog, not through bespoke CSS.
